# ADR-0008: Locate an already-approved control with one screen image

Status: implemented locally; review pending; NOT TESTED ON PHONE.
Task: t_cfbe3719. Branch: `feat/vision-locate`, based on the files/attachments branch.

## Decision

Accessibility is first. Only an immutable approved `tap_text` / `type_text` (including the registry equivalents `CLICK_TEXT` / `TYPE_TEXT`) can reach vision, and only after GenericAppAutomator's existing typed NodeNotFound retries are exhausted. A rejected action, lost service, takeover, id-based action, messaging donor sub-operation, or planner failure cannot trigger vision. Nothing changes the approved action, label, text or app. For typing, a successful locate taps the field and the existing accessibility path enters only the approved text into an actually focused, non-password input; if none exists, the step fails.

The setting “Let EQO look at the screen when it cannot find a button” is off by default. It explains the full-screen image upload, the configured AI provider's privacy policy, protection refusals, no local retention, and six attempts per run. Its consent flag is captured in ApprovedTaskPlan at preview time, not read as new permission during execution. Every eligible preview line explains that an image may be sent. A vision-enabled plan requires an explicit plan approval even if the ordinary approval preference is off. Turning vision on after preview cannot authorize that run; turning it off during a run prevents a capture/upload/tap not yet dispatched.

One VisionLocateRun lives for one foreground run. It counts all requested locates, including refused ones, with a hard cap of six. One step cannot repeat its locate or gesture. One locate captures at most one screen. There are no provider retries or alternative models: the exact configured OpenRouter model is checked against the existing public model metadata (`architecture.input_modalities` explicitly contains `image`). Unknown or text-only models fail with a plain explanation before capture. Metadata caching contains public model information only, never images. No new runtime or dependency is added.

The request/parser lives in core-llm and the policy in core-agent. The model receives just one ephemeral JPEG plus the JSON-quoted approved label, not the plan history, typed contents, a tool list, or a replanning request. It must return only four integer screenshot-pixel box edges or NOT_FOUND. Extra prose, JSON actions, tool requests, markdown, negative/fractional coordinates and oversized replies are rejected, not interpreted. The box must have positive area, fit the captured display and active app window, and overlap neither an EQO window nor another app/system window. The Android edge independently repeats these checks and the live gate immediately before dispatch.

## Screen privacy and action gates

- Reuse the service's same `captureBitmap` / Android `takeScreenshot` path used by ScreenshotCapture's saved-file writer, but encode entirely in memory: never call the saved-file capture, write a temporary file, record `last_screenshot`, create a history message, or log image/reply contents.
- Fail-closed secure-window gate (round-2 review fix). The vision path classifies every visible window as SECURE, NOT_SECURE or UNVERIFIABLE via `VisionUploadGate`; only when *every* visible window is positively NOT_SECURE may an image be produced for upload. A SECURE window refuses with “This is a protected screen. Nothing will be sent.”; an UNVERIFIABLE window (probe missing/blocked/throwing) refuses with “EQO cannot verify that this screen is not protected, so nothing will be sent.” Unknown is never permission to upload. The gate is enforced twice: in `AndroidVisionLocateScreen.state()` before any window tree is inspected, and again in `EQOAccessibilityService.captureVisionFrame` immediately before and after the Android `takeScreenshot` call, so a successful-but-redacted or otherwise unverifiable capture yields no image. Capture failure is never bypassed. This is scoped to the new upload path; the inherited screen-text probe keeps its recorded SF-2 behaviour. There is no reliable semantic “banking app” detector or newly invented banking deny list.
- Inspect all exposed visible windows, not just the active root, for password fields. Any missing/unidentified window root, uncheckably complex tree, non-probe EQO window, secure screen or takeover fails closed. A 1x1 EQO takeover probe is not an approval surface; its rectangle is still excluded from possible boxes. Other apps' and system windows' rectangles (including keyboards/overlays) are excluded too, so a box cannot select another window merely because it overlaps the active app's full-screen bounds. Password contents and EQO's own tree text are not read into the signature. An OEM that hides a window root may therefore make vision unavailable; do not bypass that refusal.
- Compare an ephemeral SHA-256 node-tree digest, window identities/bounds, app and display size around capture and after the model wait. A changed screen discards the result. Check the privacy/permission state again before upload and immediately before tap. Signatures are never logged/persisted and no screen text is sent separately.
- Enclose the accessibility retries, capture and provider wait in the existing agent-action window so physical takeover during an AI wait is observed. The tap uses GatedServiceActions and the existing dispatchGesture callback/grace bookkeeping. Read-only privacy checks do not mint additional touch grace. Existing Pause/Stop/irreversible-in-flight rules remain unchanged; cancellation checks prevent a cancelled reversible locate from dispatching later.
- Wait for gesture settling, then require a changed node-tree signature in the same app. An unchanged/protected/different-app result is a failed locate, not success, and is non-transient so the loop cannot repeat its gesture. A changed signature is not proof that a purchase/send was delivered; normal postcondition limitations still apply.
- The per-action hard bound is extended to 60 seconds only for approved vision-eligible text actions; every other action retains its existing bound. The public metadata request is bounded at 20 seconds and the single image request at 30 seconds. All locate diagnostics are exactly `vision locate: attempt N, result found/not-found/refused`. Raw provider replies, exception messages, labels, tree digests, coordinate replies and image bytes never enter locate diagnostics.

The secure-window primitive is a positive probe only: `AccessibilityWindowInfo.isSecure()` is not in the public SDK (verified with `javap --classpath platforms/android-36/android.jar`; the round-2 review found no public method in the AOSP `android-11.0.0_r1` tag either), so on stock builds the reflective probe is hidden/blocked and every window is UNVERIFIABLE — which now refuses vision rather than uploading. `ERROR_TAKE_SCREENSHOT_SECURE_WINDOW` is API 34+ (`platforms/android-36/data/api-versions.xml`), so it is only an additional refusal signal, never a permission. Consequence and supported-version limit: vision locate runs only where a platform returns a trustworthy secure flag; where it cannot be verified, vision refuses with the plain reason above (fail-closed) and the secure-screen guarantee is never silently downgraded. The inherited reflective secure-window limitation for the *screen-text* path is recorded in `android/Phase-One/evidence/task-012-action-loop.md` (SF-2). Unit tests prove the fail-closed decision, not any particular phone's FLAG_SECURE capture behaviour; hidden/OEM behaviour must pass the supervised protected-screen check before release, and SDK compilation is not evidence that banking/authenticator screens are safe to upload.

## Threat model: on-screen prompt injection

A page, app, notification or label can instruct the model to ignore the task, approve a dialog, tap another app, type new text, or return additional steps. Both image text and the quoted label are explicitly untrusted. The model has no action tools. A strict four-number parser is the only output surface; the immutable approved plan supplies the label/text, and the local policy supplies the app, window exclusions and mutation budget. Even a valid returned box cannot authorize an additional step, helper consent, EQO approval, cross-app coordinate, or arbitrary typed content.

Residual risk: an adversarial image/model can return a geometrically valid but semantically wrong box within the current app. Bounding-box validation cannot independently prove the visual label when accessibility cannot find it. This is not a claim of perfect prompt-injection resistance. Keep vision opt-in, show the upload possibility before approval, use it only for the approved step, limit attempts, never silently repeat a gesture, and require the owner to supervise sensitive actions. Changes that allow the model to choose labels, actions, text, apps or follow-up steps require a separate security decision.

Other limits: accessibility can miss custom-rendered/unmarked password fields; a screen can change between the final inspection and OS gesture dispatch; third-party providers can retain images under their policies; device/OEM capture behaviour is unverified. “Nothing is stored” means EQO does not store the image/reply, not that the provider promises zero retention. Unlabelled icons are NOT_FOUND unless the approved label can safely identify that exact control; EQO must not substitute a neighbouring control.

## Verification

Offline fake provider and screen tests cover found/not-found, malformed/injected replies, bounds, own-window/other-app regions, secure/password/capture refusal, six-attempt cap, text-only/unknown metadata, setting off/revocation, screen races, unchanged screen, immutable approval, accessibility-first routing and unchanged typed text. The round-2 fail-closed gate is covered by `VisionUploadGateTest` (throwing/unavailable metadata → UNVERIFIABLE; only a fully verified non-secure set is sent; empty/secure/unverifiable sets refuse) and by two `VisionLocateRunTest` cases asserting zero image and zero model requests for unverifiable secure metadata and for a successful-but-rejected (redacted) capture. Android fake-tree tests cover password/secure/own-window refusal and no extra touch grace. Local check results and the Zepto/Flipkart-in-Chrome/unlabelled-icon phone checklist are recorded in `docs/agents/PHASE-ONE-TEST-LOG.md`. Full CI and real device/provider testing remain the lead's gates; this worker does not publish or merge.
