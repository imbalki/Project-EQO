# ADR-0007: Shared-storage file access, attachments and EQO screenshots

Status: implemented; unit tests with fakes pass; phone validation pending (Realme, Android 11).

## Context

The owner wants EQO to find files on the phone and send them (WhatsApp, Gmail, Messages) as part of an approved plan, and to attach a screenshot EQO just took. Android 11 scoped storage hides most shared folders from an ordinary app, and a file is shared with another app only through a content URI that EQO grants.

## Decision

- **All files access** (`MANAGE_EXTERNAL_STORAGE`) is requested only through a guided setup row. EQO never grants it to itself and never writes secure settings; the owner turns it on in Android's own page. The row is separate from the readiness rows (optional, never "next step"). EQO is sideloaded, so Google Play's restriction on this permission does not apply; the manifest entry says so and carries a targeted lint ignore.
- **Read-only file actions.** `FIND_FILES(query, folder)` and `LIST_FILES(folder)` return names, sizes and paths only, never contents, and their output is fenced as untrusted data. They need All files access outside EQO's own folders and say where to turn it on. A plain relative path such as `out/docs` keeps the earlier behaviour of listing EQO's workspace. `LIST_FILES` renamed its parameter to `folder` (`path` is still accepted).
- **Place rules** (`SharedStorageLayout`): only shared storage is reachable. EQO's private data and settings, other apps' `Android/data` and `Android/obb`, and the share staging folder are refused after resolving links. Hidden entries are skipped and links are not followed.
- **Attachments** are an optional `attachment` parameter on `SEND_EMAIL`, `SEND_WHATSAPP` and `SEND_SMS`: a file path, several separated by `|`, or `last_screenshot`. The planner validator rejects `..`, links and control characters. The plan preview names every file that will go out, so the owner approves exactly that.
- **Sharing.** Files are copied into a staging folder and served by a separate, non-exported `EqoSharedFileProvider` (authority `ai.eqo.app.sharedfiles`) that serves only that folder, not the owner's real folders. `ACTION_SEND` / `ACTION_SEND_MULTIPLE` carry `EXTRA_STREAM`, a `ClipData`, `FLAG_GRANT_READ_URI_PERMISSION`, and are aimed at one package (WhatsApp, Gmail, or the default messaging app). The existing Send-button automation then presses Send. The earlier provider (`ai.eqo.app.fileprovider`) is unchanged.
- **Cleanup.** Staged copies are removed after one hour (swept at the start of every share), immediately when opening the app fails, and when nothing could be composed. The hour leaves time for a large upload to finish after Send.
- **Screenshots.** `TAKE_SCREENSHOT` uses the accessibility service's `takeScreenshot`, saves a PNG to `Pictures/EQO` (or to EQO's private Pictures folder when All files access is off) and records it as `last_screenshot`. It is refused when a protected window (`FLAG_SECURE`) is showing, when EQO's own window is in front, and while the owner has taken over. If the window turns protected during capture the picture is deleted and not recorded.

## Limits

- The planner writes the whole plan before any step runs. Files v2 resolves an approved `find:` search at run time, rather than making up a path from a preceding `FIND_FILES` step (see below).
- WhatsApp's file preview, Google Messages' compose screen and Gmail's compose screen are driven by view ids and labels that have not been tried on the phone yet; if a Send button is not found the step reports "could not press Send" and the owner finishes it.
- The `jid` extra that opens a WhatsApp chat directly from a share is undocumented and may be ignored by some WhatsApp versions, in which case WhatsApp asks which chat to use.
- 25 MB total per send (Gmail's limit); old EQO screenshots are not deleted automatically.

## Files v2: run-time attachment resolution (t_ecfe91de)

- `AttachmentSpec` accepts a user-given path, `last_screenshot`, or `find:<words>` with comma-separated `name`, `type`, `folder` and `date` filters. Examples: `find:ebay bill`; `find:type=screenshot,date=2026-10-07`; `find:type=pdf,name=invoice,folder=Download`; `find:latest,type=image`. No unrecognized or duplicate filters, traversal, links, control characters or invalid dates. Name words all match case-insensitively. `latest` requests newest-first ordering, not permission to guess among multiple files.
- `AttachmentFileSearch` reuses `SharedStorageLayout`: only allowed shared storage, excluding other apps' data/obb, staging, hidden entries and all symlinks (including explicitly supplied folders with linked ancestors). It reads metadata only. Types are extension-based; screenshots also require Pictures/Screenshots, DCIM/Screenshots or EQO's screenshot folder. Date filters use file last-modified in the phone's local timezone, with inclusive day/range endpoints. The planner receives the local calendar date/timezone and must expand today/yesterday/last week into explicit dates before approval.
- Searches are bounded to two seconds, 50,000 visited entries, depth eight and 200 matches. Hitting a bound or an unreadable searched directory refuses the send and asks for a narrower search; a partial scan can never masquerade as one unambiguous match. Complete results sort newest first. A chooser offers at most eight results, with name, date and byte size; no path/URI enters the UI selection boundary.
- One match is resolved automatically; multiple matches require an actual human list-item tap in foreground EQO. No UI, cancellation or an invalid choice refuses with up to eight matching names so the owner can rephrase. Zero matches reports the approved search. The immutable plan still approves the search, recipient and send action; choosing a matching file does not rewrite it.
- Before staging or launching a recipient app, EQO updates the run status with the exact chosen name(s) and shows a Continue/Cancel disclosure. Continue is required even for one match. Both dialogs time out after 60 seconds; backgrounding cancels them. Approved attachment-send steps alone receive a 150-second apply budget for both waits plus search/copy/send; other actions retain their existing budget. Existing approval, own-window/obscured-touch and takeover gates remain in force; chooser row taps are explicit task controls, not a reset of takeover.
- Recheck the selected files after the human wait, then stage copies. Existing share URI grants, 25 MB cap, one-hour sweep and failure cleanup remain. Literal paths and TAKE_SCREENSHOT/last_screenshot remain supported, including the private screenshot fallback. Only count/kind diagnostic codes may be logged; search text, names and paths stay in transient local UI.
- Host verification is recorded in PHASE-ONE-TEST-LOG.md. NOT TESTED ON PHONE: real gallery metadata, OEM storage behavior, chooser lifecycle and Gmail/WhatsApp attachment Send buttons.

### OEM folder discovery and MediaStore (operator addition)

- Primary type/bucket/date metadata comes from bounded queries over MediaStore Images, Video, Audio, Downloads and Files. Only RELATIVE_PATH, DISPLAY_NAME, BUCKET_DISPLAY_NAME, MIME_TYPE, DATE_MODIFIED and DATE_ADDED are read; no content or `_data` paths. MIME and modified/added timestamps take precedence, with extension/file metadata fallback. Bucket-column incompatibility and permission/provider absence fall back safely to filesystem metadata. The filesystem scan still checks uniqueness so a stale/partial MediaStore index cannot hide a second match.
- All folder aliases, file extensions and MIME prefixes live in one asset data table: `actions-android/src/main/assets/shared-storage-aliases.json`. Includes Download/Downloads, camera and screenshot variants, modern/legacy WhatsApp and WhatsApp Business media, Telegram, Instagram, Bluetooth and Documents. `type=camera`, `type=gallery` and `type=download`/`downloads` are also accepted. The old in-code named-folder map is removed.
- On first search per phone, discover top-level/second-level allowed folder names and MediaStore bucket-to-relative-folder mappings. Persist only the category-to-folder map in local app preferences, never file names, searches or contents. Reuse the map on subsequent runs, refresh on a zero-match search, and support explicit on-demand rediscovery with `find:...,rescan=true` (documented to the planner). Media queries are capped at 20,000 metadata rows/two seconds; directory discovery is bounded, and attachment filesystem search retains its own bounds.
- OS-unreadable Android/data and Android/obb remain excluded. No workaround, permission grant, new runtime or dependency is introduced. Fake layouts cover Realme-style, Samsung-style and Xiaomi-style names; a bucket test uses a synthetic vendor-specific path outside every listed screenshot path.
